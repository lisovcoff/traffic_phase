# Конечная задача traffic_phase

Зафиксирована по указанию пользователя 2026-10-15. Этот документ задаёт цель
продукта; PROJECT_STATUS описывает достигнутую часть, а не заменяет эту цель.

Пользователь передаёт JSON либо архив траекторий **одного перекрёстка**.
Система автоматически:

1. Проверяет вход, время и покрытие; выделяет подходы и движения между ними.
   Поддерживает 3/4 подхода, в том числе непрямоугольные/необычные конфигурации;
   отсутствие потока не доказывает отсутствие подхода.
2. Определяет число логических фаз, их порядок и состав движений, включая
   shared movements. Не ограничивается K2/K3 и не требует ручных A/B/C.
3. Восстанавливает возможный состав светофоров/секций на подходах: обычные,
   с одной или несколькими допсекциями. Учитывает отдельные направления/полосы;
   один подход не обязательно означает один физический светофор.
4. Восстанавливает локальную временную историю, включая продления/сокращения,
   отклонения от обычного цикла и изменения режима. Причина (спецтранспорт,
   нагрузка, ДТП и т.п.) не назначается без подтверждающего evidence.
5. Показывает результат в HTML, например через FastAPI: схема перекрёстка,
   состав фаз, светофоры/секции, временная шкала, отклонения, происхождение
   вывода и неопределённость. Все интерфейсы используют одинаковую семантику.

Обычный вход продукта остаётся JSON/архивом. Независимые видео/журналы и
calibration нужны для разработки и проверки качества; это не замена продукта
ручной разметкой каждого входного файла. Дополнительная проверенная схема
может уточнять неоднозначные результаты и не должна игнорироваться.

По одним траекториям не всегда различимы аппаратная стрелка, permissive поворот,
погашенная секция, отсутствие спроса и блокировка. В таких случаях продукт
сохраняет альтернативы/UNKNOWN, отдельно выдавая оценку логической фазы.
Нельзя обещать однозначное восстановление всех ламп для любого входа.
Это ограничение доказательств, а не отказ от автоматизации остальных шагов.

«Все нюансы РФ» должны стать версионируемой матрицей поддерживаемых сценариев:
основные/дополнительные секции, переходы и мигание, разрешённое движение с
уступанием, пешеходные конфликты, межфазные интервалы, адаптивное/вызывное
управление, приоритет, смена плана, блокировка/сбой и отсутствие наблюдений.
Специальные сигналы (например, трамвайные/реверсивные) требуют отдельной строки
поддержки, входных признаков и проверки. UNKNOWN/unsupported должен быть явным.
Распознавание режима не означает установление его причины.

Завершение проекта требует проверенного end-to-end сценария на независимых
реальных сеансах, отдельно по K, составу фаз, topology/секциям, временным
границам, coverage/UNKNOWN и HTML-согласованности. Наличие API, число unit-тестов
или synthetic success не заменяют эту приёмку. Численные SLA и объём validation
фиксируются до оценки по протоколу; текущие известные записи — development.

Приоритет ближайшей работы: независимый calibration-пилот по
VALIDATION_PROTOCOL.md §8, затем ограниченная проверка согласованной модели
на отдельном validation session. Самостоятельные эксперименты вне этих целей
не являются приближением к приёмке. Новые эксперименты требуют следующего задания.

Уточнение по заданию 2026-10-15: разрешён один bounded event-time шаг устранения
раннего restart proxy, с сохранением default и старых результатов. Затем работа
должна вернуться к проверяемой цепочке K/composition/local history; повторная
диагностика тех же семи машин не является самостоятельной целью. Сводный
критический путь находится в начале корневого ROADMAP.md.
