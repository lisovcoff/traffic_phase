## Пять наиболее критичных проблем

### P1 — событие автомобиля не измеряет момент переключения лампы

**Файлы/функции:** `app/core/v9/events.py::_track_event_view`,
`_kinematic_release_candidate`, `load_event_streams`;
`app/core/v9/model.py::_choose_phase_evidence`.

**Механизм:** при недостаточном количестве release-событий весь набор
подменяется смешанными entry/restart событиями. Вход в зону зависит от геометрии,
спроса и пробки; возобновление движения может быть снятием блокировки после ДТП
или разрешённым поворотом. `entry + stay` и image-space restart не являются
пересечением стоп-линии. В packed release streams остаются timestamps, но
потеряна индивидуальная оценка confidence/method. Систематическое запаздывание
реакции и рассасывания очереди не оценено как неопределённость времени лампы.

**Подтверждение:** прочитан ограниченный префикс 262144 байта реального
`6_2025_2_17_16.json`, декодированы 4 полных трека, незавершённый пятый отброшен.
Три main events — `input_zone_entry`, один — `metadata_dwell_end_restart`.
Это проверка механизма, а не репрезентативная оценка частот по архиву.
Есть `line_in/out`, centroid, lat/lng, millis и zone; семантика line-полей
и их связь со стоп-линией не подтверждены. В compatibility stack уже есть
`trajectory_events.py::extract_trajectory_events` со stop_line_provider;
дублирующий новый извлекатель не нужен без сравнения контрактов.

**Исправление:** сохранить тип, provenance, confidence и интервал времени
каждого события; использовать проверенную геометрию стоп-линии, если доступна.
Entry оставить признаком спроса. Release считать косвенным свидетельством с
моделью задержки по движению/очереди. Отсутствие спроса и блокировку моделировать
отдельно от состояния сигнала; без различимости выдавать UNKNOWN.

**Приёмка:** тесты на одинаковую траекторию при permissive turn, блокировке и
разгрузке очереди не дают безусловного GREEN; потеря release у одного потока
не меняет семантику всех остальных. Оценка ошибок времени проводится только
на независимых stop-line/ламповых метках, с интервалами неопределённости.

### P2 — гипотеза активности превращается в физический сигнал и уверенность

**Файлы/функции:** `app/core/v9/signal_renderer.py::signal_state_at`,
`app/core/v10/automatic_physical.py::infer_physical_signal_plan`, `_head_states`;
`app/core/v10/semantic_mapping.py::signal_state_at`;
`scripts/v9_spatial_visualizer.py::_physical_visual_model`, JS
`movementInfo`, `physicalSectionState`, `physicalHeadInfo`.

**Механизм:** вероятность события выше порога становится GREEN, ниже — RED.
Activity/confidence не является вероятностью лампы. Повороты переводятся в
физические стрелки; empty phase наследует green предыдущей поддержанной фазы.
Head state для неподтверждённого main становится RED. Рендерер добавляет
YELLOW=3s и RED_YELLOW=2s в границах активной стадии; JS physical path выдаёт
probability 0/1. Нет доказательств таких аппаратных переходов или all-red.
Документация Stage 2 уже запрещает однозначно выводить стрелку из интервала
движения, но canonical V9/V10 path этот контракт не обеспечивает.

**Подтверждение:** диагностический план с activity N->S=0,4/0 даёт GREEN при
t=20, RED при t=70, RED_YELLOW при t=1 и YELLOW при t=49 без меток ламп.
Compatibility `SignalStateEstimator` имеет UNKNOWN и safety tests, но успешные
тесты этого стека не доказывают консервативность отдельного V9 visualizer.

**Исправление:** единый контракт состояния секции с `state`, вероятностями
известных состояний, отдельной uncertainty/abstention, временным интервалом и
source (`observed`, `inferred`, `configured`, `simulated`). Разделить logical
group и hardware head; поворот не доказывает дополнительную секцию. Empty/no-demand
не наследует GREEN без свидетельств. Переходные времена допускаются как
явная конфигурация симуляции, а при реконструкции без измерения — UNKNOWN.
UNKNOWN показывается нейтрально и сохраняется в API, timeline и HTML.

**Существующее исправление визуализатора:** проверен diff ветки
`fix/respect-explicit-physical-plan-20261012`, commit `cb10466`.
`build_spatial_visualization` в main повторно присваивает physical_plan из
result после чтения `physical_plan_path`. Указанная ветка заменяет это на
fallback только при None, сохраняя в том числе `enabled:false`.
Ветка не является предком проверенного main. На этапе 2 использовать уже
существующее исправление после проверки совместимости; не писать его повторно.
В этой ветке кода визуализатора не меняли.

**Приёмка:** пустые/слабые потоки дают UNKNOWN; permissive turn не создаёт
аппаратную стрелку; заданные и выведенные планы имеют разные provenance.
Проверить builder для explicit enabled/disabled/missing plan и равенство
состояния Python/API/HTML на одних timestamps. Уже существующие renderer tests
нужно расширить проверками доказательств, а не только ожидаемого цвета.

### P3 — периодический baseline заменяет фактическую временную историю

**Файлы/функции:** `app/core/v9/decoder.py::decode_cyclic_hsmm`,
`app/core/v9/events.py::periodic_baseline_from_segments`,
`app/core/v9/model.py::_local_regime_selection`, `_discover_from_stream_views`;
`app/core/v9/signal_renderer.py::build_signal_model`, `_find_segment`;
`app/core/v9/online.py::OnlinePhaseTracker.infer`.

**Механизм:** HSMM допускает лишь последовательность `(phase-1)%k` с bounded
durations. Пропуск, аварийная передача приоритета и длинное удержание вне bounds
не выражаются штатно. Baseline усредняет начала modulo одного T; renderer
берёт `baseline_segments`, а временные отклонения остаются отдельной диагностикой.
Он не читает raw_hsmm_segments как фактическую историю. Для длинного архива
выбирается одно представительное часовое окно доминирующего режима, а не
восстанавливаются все часы. Online корректирует общий shift baseline, что не
эквивалентно независимому удержанию/пропуску фазы. `_find_segment` вне покрытия
возвращает последний сегмент (на диагностике t=120 вернул RED после end=100).

**Исправление:** сохранить baseline как prior; отдельным результатом отдавать
историю локальных режимов, per-cycle границы и покрытие каждого интервала.
Рендерить реконструированную историю с UNKNOWN в пробелах. Расширять существующий
decoder минимально: явные разрешённые skip/hold transitions и bounds от
конфигурации, с диагностикой out-of-model. Не переписывать весь стек в новый ML
framework. Онлайн модель обучается только на прошлой калибровочной истории.

**Приёмка:** extension +10/+30s, omitted phase, смена режима, отсутствие событий,
обрезанные циклы и gaps не заменяются обычным циклом; timestamps вне покрытия
дают UNKNOWN. Prefix invariance: добавление будущих событий не меняет уже
выданный causal результат. Причина отклонения остаётся UNKNOWN без внешних
данных; ДТП нельзя классифицировать только по сдвигу.

### P4 — жёсткий topology cap исключает корректную структуру до сравнения

**Файлы/функции:** `app/core/v9/fit.py::discover_phase_count`;
`app/core/v9/model.py::_discover_from_stream_views` (3→2 redundancy).

**Механизм:** если имеются N->S, S->N, E->W, W->E, `upper=min(upper,3)`.
Даже идеальный четырёхфазный перекрёсток с защищёнными поворотами не может
выбрать K=4. Default kmax=6 исключает K7/8 отдельно. README о direction-agnostic
discovery недостаточно описывает это ограничение. 3→2 redundancy добавляет
второе место возможного потери подфазы, но частоту его ошибок не измеряли.

**Подтверждение:** spy em_fit/candidate_metrics без обучения при четырёх прямых
потоках зарегистрировал только кандидаты `[2,3]`. Старые проценты K≥5 нельзя
переносить на этот новый код, однако ограничение кандидатов подтверждено прямо.

**Исправление:** hard cap заменить мягким, диагностируемым prior и бюджетом
кандидатов, заданным конфигурацией и наблюдаемостью. Сохранять причины исключения
K и альтернативные модели. Merge принимает улучшение likelihood/support с
учётом независимых protected intervals, а не только cardinal geometry.

**Приёмка:** четырёхфазный кейс с четырьмя прямыми и защищёнными поворотами
реально рассматривает и выбирает K4; переименование потоков не меняет K.
K5–8 проверяются отдельно при включённом диапазоне. Sparse данные дают
неопределённую структуру, а не искусственно уверенный K2. Контроль расхода
времени — ограниченный shortlist, без полного гиперпараметрического перебора.

### P5 — существующие метрики не валидируют физические сигналы независимо

**Файлы/функции:** `app/core/v9/evaluate.py::evaluate`, `_state_at_time`;
`app/core/v9/model.py::_discover_from_stream_views` (evaluation baseline);
`scripts/ci_lenina_regression.py::main`; validation-pack CSV/report.

**Механизм:** `evaluate` выбирает лучшую перестановку фаз по тем же меткам,
на которых считает `continuous_accuracy_percent`; это допустимая permutation-
invariant cluster agreement, но не независимая точность семантики ламп.
Метрика измеряет baseline phase, не основную/дополнительную секцию, и не
разделяет UNKNOWN/coverage. `_state_at_time` заполняет внепокрытийное время
крайним состоянием. Границы marks не проверяются на сортировку/конфликты.
Lenina CI сознательно использует envelopes, полученные из известной ручной
разметки; это регрессия development-case, а не внешний тест. Сам код discovery
передаёт marks только в evaluation: прямую утечку marks в fitting не подтвердили.
CSV/report имеют численное расхождение, описанное выше.

**Исправление:** сохранить старую метрику под явным именем cluster agreement;
для физических секций зафиксировать semantic mapping на train/calibration,
разметку test открыть только evaluator. Добавить group/time split manifest,
дедупликацию архивных копий, метрики по секциям/секундам и coverage, независимую
разметку ламп с неопределённостью. Известные архивы остаются regression suite.
Подробный контракт — в `VALIDATION_PROTOCOL.md`.

**Приёмка:** test не подбирает mapping, offset, threshold или plan; смена
test labels не меняет predictions. Зафиксированный split проходит проверку
пересечений source/session/track. Все агрегаты пересчитываются из одного набора
поэлементных результатов. Никакое совпадение K не называется lamp accuracy.

## Последовательность дальнейшей разработки

Уточнение пользователя от 2026-10-13: приоритет — точность алгоритма;
FastAPI, визуализация и интеграция откладываются до проверки ядра на разметке.
Сначала создавать offline evaluator и машинно проверяемые результаты, без
разработки UI. Максимальную точность измерять на независимом holdout, а не
добиваться максимального совпадения с тремя известными файлами.

| Этап | Работа | Критерий завершения |
| --- | --- | --- |
| 2A | Зафиксировать каноническую ветку, зависимости, схемы времени/событий, семантику ручных меток и split manifest; создать offline baseline evaluation | Воспроизводимые ошибки K, границ и состояний с coverage; ручные метки не попадают в inference |
| 2B | P1: качественные события и интервалы задержки; P2: UNKNOWN и logical/physical distinction в ядре | Контрпримеры движения без зелёного проходят; offline результат сохраняет uncertainty и provenance |
| 2C | P4: снять жёсткие caps, консервативный выбор/слияние моделей | K4 и rename invariance; диапазон K5+ явно описан и проверен |
| 2D | P3: фактическая временная история и multiple regimes, causal replay без web-интеграции | Skip/hold/длинные gaps не заменяются baseline; prefix invariance |
| 2E | P5: независимая оценка и calibration | Protocol gates, per-head confusion/coverage, CI из единого manifest |
| 2F | Ограниченный размеченный пилот алгоритма, ошибки по сценариям и ресурсные проверки ядра | Protocol gates, независимый holdout и границы применимости; измеренные RAM/latency |
| 3, отдельное задание после приёмки ядра | FastAPI, визуализация и интеграция; применить существующий fix explicit plan после проверки совместимости | API/HTML точно воспроизводят результат ядра, UNKNOWN и временную шкалу; UI не выводит собственные состояния |

Не совмещать все этапы в одну переработку. Для этапа 2 сначала минимальные
контракты и воспроизводимые failing cases, затем небольшие независимые исправления.
На этапе 1 dependencies не устанавливаются, inference на полном архиве,
обучение и parameter search не запускаются.

Преобразование Unix milliseconds в UTC+5 совпадает с `timestamp_local`.
Использовать `timestamp_ms` для вычислений; часовой пояс записи —
`Asia/Yekaterinburg` (Челябинск), только для отображения. Этот результат
подтверждает внутреннюю согласованность файлов, а не физическую синхронизацию
камеры и контроллера. До первой метки и после последней truth UNKNOWN;
начальное start_ms само по себе не задаёт состояние фазы.

Сообщённая пользователем семантика этих записей:

* Две фазы: светофоры без дополнительных секций. Это предоставленная информация
  о данных, а не универсальное правило «K2 означает отсутствие стрелок».
* Три фазы: `{N->_S, S->_N}`, `{E->_W, W->_E}`,
  `{N->_S, N->_E, E->_N}`. Нормализация `_` допустима внутри алгоритма,
  исходные обозначения сохраняются в provenance. Третья группа разделяет
  N->_S с первой: состояния/группы нельзя моделировать как непересекающиеся OD.
* Перечисление фаз пользователем не задаёт соответствие букв A/B/C их
  движениям и не задаёт временной порядок. В старой Git fixture
  `tests/fixtures/lenina_physical_signal_plan.json` A=turn group, B=NS,
  C=EW, но C также содержит W->N. Поэтому это только исторический кандидат
  mapping, не новая истина для найденной разметки. Требуется сверка с
  происхождением меток; не выбирать mapping по тестовой accuracy.

Файлы содержат `kind`, `timestamp_ms`, `timestamp_local`, `offset_s`, `order`,
но не описание способа наблюдения, error tolerance, состояния YELLOW/OFF,
hardware IDs или отдельные переходы основной/дополнительной секции.
Теперь ручная разметка фаз доступна; утверждение об отсутствии любых меток
больше неприменимо. Независимость ламповой истины и детализация аппаратных
состояний по-прежнему не подтверждены. Дополнение проверено стандартной
библиотекой Python, без обучения и новых зависимостей.

Нужны независимые timestamped состояния ламп по основным и дополнительным
секциям, аппаратная топология/stop-line geometry и clock synchronization;
значения/единицы line_in/out, speed, centroid/lat/lng и semantics durations;
разметка случаев ДТП, адаптивного управления и ручного вмешательства;
run manifests старых CSV и происхождение archive K truth; отдельный заявленный
технический аудит, если он существует. Аппаратную схему нельзя восстановить
единственным образом из совпадающих OD-времён. Без этих материалов можно
проверять гипотезы потоков и software invariants, но нельзя заявлять 99% точности
посекундного сигнала. Создание документов завершает этап 1.
