**Решение: продолжать проект, исправить контракт наблюдений и остановить полный перебор как путь к production.** Сохранить его как эталон для малых задач. Оснований принимать 2D.1 или публиковать lamp accuracy нет; оснований объявлять бесполезной автоматизацию по траекториям тоже нет.

Я прочитал ZIP, перечисленные модули, тесты, ROADMAP и документы протоколов. GitHub доступен: новая ветка указывает на [`c0e8946`](https://github.com/lisovcoff/traffic_phase/commit/c0e89461c0bc28f2d7fd9609b07a591a50195bbf), на два коммита после указанной базы; изменений `app` между ними нет. Четыре основных модуля ZIP совпадают с GitHub по Git blob SHA.

Проверка включала:

- совпадение всех **62 хэшей** из seals;
- запуск **80 тестов — все прошли**; три отсутствовавших в ZIP служебных модуля загружены из базовой ревизии;
- независимый пересчёт **93 024 path likelihood** и обоих posterior для всех 15 complete cases: максимальное расхождение log-likelihood `2.3e−13`, posterior `6.3e−15`;
- независимый пересчёт boundary matching и условных интервалов.

Это аудит данного экспериментального контура. Реальные видео/траектории в ZIP отсутствуют; их timing truth, исторические real-метрики и сквозной HTML/API я не проверял. Хэши подтверждают согласованность пакета, но сами по себе не доказывают всю историю его получения.

**Пять приоритетных findings**

1. **P1 — bridge не согласует область query с областью наблюдений likelihood. Реальный дефект контракта.**

   Места: `LocalEvidenceIndex.query`, [`prepare_joint_observation`](https://github.com/lisovcoff/traffic_phase/blob/41563f5852ec2708a0db6a590d04888b256baae9/app/experimental/phase_observation_bridge.py), `rounded_components.pattern`.

   Query отрезает события по `range_ms`. Bridge использует supplied camera windows, но не проверяет, что query действительно доставил все события из этих окон. Отсутствующая отметка становится *недетекцией*, хотя могла быть просто отрезана запросом.

   **Воспроизведённый контрпример:** один автомобиль, RELEASE=6.250 с, CROSSING_PROXY=8.250 с, transit=2 с, обе detection probabilities=1, camera window `[0,20)`.

   - `query(0,8000)` → `TRACK_PATTERN_UNSUPPORTED_BY_DELAY_DETECTION_MODEL`;
   - `query(0,20000)` → `ready_for_declared_model_only`.

   Более опасен тихий вариант: пустой query `[0,2)` принимается с observation window `[0,8)`. Для постоянных интенсивностей `.2+.03` и release detection=1 получается compensator **−1.84**, хотя доступный двухсекундный участок даёт **−0.46**. Шесть недоставленных секунд используются как отрицательное свидетельство.

   **Исправление:** либо требовать подтверждённую полноту query относительно всех моделируемых каналов, либо включать механизм отбора query в observation kernel и compensator. Для rounded timestamps недостаточно механически пересечь интервалы истинного времени: отбор выполняется по округлённой отметке.

2. **P1 — stationary phase start не устраняет левое цензурирование популяции автомобилей. Ограничение модели для реальных окон.**

   Место: [`rounded_components`](https://github.com/lisovcoff/traffic_phase/blob/41563f5852ec2708a0db6a590d04888b256baae9/app/experimental/rounded_observation.py), интегрирование только по `u∈[0,h)`.

   **Воспроизведённый контрпример:** latent vehicle time `u=−1.750 с`, release delay=2 с, наблюдаемый RELEASE=0.250 с. Такой автомобиль естественно попадает в начало вырезки непрерывной записи. Код возвращает `TRACK_PATTERN_UNSUPPORTED_BY_DELAY_DETECTION_MODEL`: вся допустимая латентная масса находится до нуля.

   Это **не ошибка интеграла внутри объявленной finite-population модели**: ограничение явно написано. Но оно блокирует её прямое применение к произвольным локальным окнам. Маргинализация возраста начальной фазы решает другую задачу.

   **Исправление:** латентная предыстория с согласованной фазовой моделью и достаточным observation context либо явно цензурируемая краевая зона без публикации оценок. Простого добавления событий в query недостаточно. Перекрывающиеся окна также нельзя считать независимыми: один автомобиль должен сохранять общую идентичность.

3. **P1 — полный enumeration непригоден уже для многих окон короче минуты.**

   Место: [`enumerate_sequences`](https://github.com/lisovcoff/traffic_phase/blob/41563f5852ec2708a0db6a590d04888b256baae9/app/experimental/unanchored_sequence.py).

   Независимый подсчёт всех допустимых путей при текущей поддержке длительностей:

   | Горизонт | K2 | K3 |
   |---|---:|---:|
   | 34 с | 5 168 | 7 752 |
   | 36 с | 8 362 | 12 543 |
   | 38 с | 13 530 | 20 295 |
   | 60 с | 2 692 452 | 4 038 678 |
   | 64 с | 7 048 870 | 10 573 305 |

   Значит, `max_paths=10000` гарантированно отказывает K3 уже на 36 с, K2 — на 38 с, независимо от информативности событий. Сохранённый hold+30 подтверждает этот механизм.

   Отказ без частичного posterior реализован правильно. **Увеличение бюджета не является решением для минут/часов.** Отдельно: поддержка полных длительностей 4…48 с исключает более длинный hold независимо от вычислителя. Это ограничение нужно пересматривать по новым данным, не подбирать по знакомой разметке.

4. **P1 — один likelihood term на автомобиль исправляет двойной счёт, но не делает detection/demand модель проверенной.**

   Места: `rounded_components.detection/pattern`, [`path_loglik`](https://github.com/lisovcoff/traffic_phase/blob/41563f5852ec2708a0db6a590d04888b256baae9/app/experimental/joint_track_model.py).

   Код предполагает условно независимые Bernoulli detection каналов и произведение распределений release delay/transit delay.

   **Аналитический контрпример:** автомобиль с вероятностью ½ полностью скрыт, с вероятностью ½ виден в обоих каналах. Маргинально `pr=pc=.5`, но:

   - истинное `P(any detection)=.5`;
   - код получает `.75`;
   - код допускает одиночные отметки с вероятностями `.25/.25`, хотя в этом механизме их вероятность нулевая.

   Следовательно, ошибаются и pattern probabilities, и compensator. Аналогично, движение колонной/разрядка очереди не обязаны соответствовать независимому Poisson-потоку с постоянной интенсивностью внутри фазы.

   Это **контрпример переносимости допущений, а не обнаруженная ошибка арифметики**. На имеющихся данных частота такого механизма неизвестна.

   Ещё одна точная неоднозначность: likelihood зависит от произведения `rate × demand exposure`. Замена `rate→c·rate`, `exposure→exposure/c` оставляет его неизменным. Отдельно восстановить оба компонента без дополнительных ограничений нельзя. Однако наблюдаемые прибытия, очередь, остановки и пропуск через зону позволяют практически ограничить demand; это не повод отказываться от всей задачи.

5. **P2 — условные интервалы не являются готовым правилом выдачи результата.**

   Места: `infer_unanchored` и [`check_sparse_duration.evaluate`](https://github.com/lisovcoff/traffic_phase/blob/c0e89461c0bc28f2d7fd9609b07a591a50195bbf/scripts/check_sparse_duration.py).

   Независимый пересчёт подтвердил:

   | Core12 | flat | soft |
   |---|---:|---:|
   | PASS по recall≥.8 | 8/12 | 7/12 |
   | matched / truth / predicted | 29/34/30 | 29/34/32 |
   | Точное число переходов | **9/12** | **8/12** |
   | Интервалы при истинном count содержат truth | 33/34 | 33/34 |
   | Median / p95 ширины | 2 / 8.7 с | 2 / 8.7 с |

   **Контрпример из сохранённого posterior:** `K3_shortening_seed23`, truth `[4,10,20,30]`; flat MAP `[8,20]`, soft MAP `[4,8,20]`. Вероятность истинного count=4 составляет всего **.073/.265**. Интервалы после условного выбора count=4 не описывают выдаваемую MAP-историю.

   Отчёт это честно оговаривает; ошибки расчёта здесь нет. Недостаёт **приёмки выдаваемого без truth результата**: count alternatives, вероятности существования границ, правила abstention и оценки пропущенных/лишних переходов. Нельзя заменить её oracle-conditioned coverage.

**Что математически корректно**

Для заявленной модели реализовано правильное выражение, с точностью до констант, не зависящих от пути:

\[
\ell(z)=
-\sum_m\int \lambda_m(u\mid z)\,p_{\rm det}(u)\,du
+\sum_i\log\int \lambda_{m_i}(u\mid z)\,q_i(u)\,du.
\]

Compensator относится к автомобилям, обнаруженным хотя бы одним каналом; пара отметок входит через один совместный kernel. Пересечения rounding cells, delay atoms и camera windows интегрируются кусочно точно. Отсутствующая отметка внутри доступного канала получает вероятность недетекции, за пределами камеры — цензурирования. Это корректно **при корректно заданной доступности**, с оговорками findings 1–2.

В `renewal_log_prior` также не нашёл ошибки:

- начальный residual \(P(R=r)=P(D\ge r)/E[D/2]\) соответствует заявленному stationary **grid** sampling;
- нулевой count использует \(P(R\ge h)\);
- последний сегмент использует survival, а не вероятность завершённой длительности;
- граница ровно в `h` правильно исключается из внутренних переходов.

Дополнительно проверил сумму prior по всем путям на 16, 24 и 34 с: единица с численной погрешностью. Uniform initial phase корректен при одинаковом распределении длительностей фаз; при разных средних длительностях потребуется другая stationary occupancy.

Тесты подтверждают эти инженерные свойства, дедупликацию, отказы и численную согласованность. Они не подтверждают реальную Poisson-модель, detector calibration, K/mapping/order или соответствие latent regime физическому сигналу. Положительные off-phase rates допускают движение до GREEN, но не оценивают его причину.

**Как заменить enumeration без ложного обещания ordinary DP**

Для общего joint-track kernel обычного состояния `(phase, age)` недостаточно:

\[
\log\mu_i(z)=\log\left(\sum_j w_{ij}\lambda_{m_i,j}(z_j)\right).
\]

Два префикса с одинаковыми текущими phase/age могут иметь разные накопленные вклады в ещё не завершённый track factor. Объединить их одним scalar score нельзя: будущая добавка находится **внутри** логарифма.

Но есть конкретная factorization:

- compensator раскладывается по временным ячейкам;
- фактор автомобиля зависит только от ячеек, где `q[i,j]>0`;
- его можно завершить на последней такой ячейке.

Поэтому при ограниченной ширине kernel допустим **semi-Markov DP с расширенным состоянием**, сохраняющим необходимую историю фаз для незавершённых факторов. Точность сохраняется; сложность экспоненциальна по ширине этой истории, а не по всей длительности записи. Если каждый kernel лежит в одной ячейке, получается обычный локальный emission и обычный semi-Markov DP. Sparse suite с нулевыми delays близок именно к этому простому случаю.

Для широких kernels практичнее bounded beam по префиксам с накопленными \(\mu_i\). Но:

- размер beam и стабильность MAP не измеряют потерянную posterior mass;
- нужны upper bounds на массы отброшенных поддеревьев;
- при сохранённой массе \(Z_{\rm kept}\) и верхней границе отброшенной массы \(U\) можно сообщать
  \[
  P(\text{discarded})\le U/(Z_{\rm kept}+U).
  \]
- если bound слишком широк, результат остаётся approximate/uncertified, без заявления exact coverage.

Для bounds можно использовать максимально возможный оставшийся вклад каждого track factor и границу compensator. Они могут оказаться рыхлыми — это нужно измерить. Для часов следует выдавать компактные marginal/alternative summaries, а не все полные пути.

**Один следующий scope**

Предлагаю **один frozen end-to-end пилот локальной истории на новых непрерывных реальных сеансах**, с фиксированной структурой фаз, чтобы отдельно проверить observation model и масштабирование. Не новый synthetic recovery suite и не повторная настройка extractor на восьми машинах.

В scope:

- исправить completeness/censoring contract;
- реализовать bounded inference с указанной factorization или честными bounds;
- сохранить extractor и оба duration priors;
- оценить observation nuisance parameters только на отдельной calibration session;
- один раз обработать untouched validation session и показать результат через существующий HTML/API;
- сравнить с замороженным повторением обычного цикла: улучшение должно проявиться именно на локальных отклонениях.

**Данные:** уже имеются реализация событий, provenance, operator mapping H1 и полезные контрпримеры. Недостаёт новых непрерывных JSON+video/controller данных, независимой синхронизации с оценкой ошибки, наблюдаемости demand/очереди и truth для проверяемых сигналов. Нужны отдельные calibration/validation sessions; для пилота — хотя бы 20 полных циклов и 50 проверяемых переходов в validation, включая реальные изменения длительности. Если доступен только H1, результат ограничивается соответствующими движениями: полное K/composition перекрёстка не считается проверенным.

Предлагаемые критерии следует заморозить **до просмотра validation**:

| Измерение | Критерий пилота |
|---|---|
| Point accuracy | One-to-one matching ±2 с; precision≥.90, recall≥.80 в каждом заранее выбранном информативном блоке. UNKNOWN учитывается как отсутствие предсказания |
| Count | Отдельно exact-count и лишние/пропущенные переходы; интервалы не компенсируют провал point gate |
| Intervals | Выдаются без truth count. Для заявленных 90% интервалов: containment≥.90, median width≤4 с, p95≤8 с; отдельно число невыданных и ложных границ |
| UNKNOWN | Отдельно логический и физический, по времени и событиям. Для заранее определённых наблюдаемых участков — логический UNKNOWN≤30%; gaps/непроверенная аппаратная семантика не принуждаются к состоянию |
| Approximation | Posterior claims только при контролируемой отброшенной массе, например ≤1%; иначе явный uncertified/UNKNOWN |
| Runtime | На объявленном оборудовании 10 минут данных ≤60 с end-to-end, peak RSS≤512 MiB; отдельный часовой проход ≤6 минут с ограниченной памятью |
| Польза | Улучшение локальных отклонений относительно frozen recurring-plan baseline при сопоставимом UNKNOWN |

Это **предлагаемые пороги**, не достигнутые результаты. Coverage на таком пилоте ещё не доказывает калибровку; нужны доверительные интервалы с учётом зависимости внутри сеансов. Ошибку синхронизации следует включать в temporal uncertainty, а не игнорировать ради допуска ±2 с.

**Путь к MVP и к высокой точности различается**

Для usable MVP уже оправдана автоматическая выдача наблюдаемых движений, траекторий, method-specific событий, счётчиков, известных пропусков данных и provenance. Геометрия относится к наблюдаемым подходам: отсутствие машин не исключает ненаблюдавшийся подход.

Следующий полезный уровень — кандидаты K/состава/порядка, shared movements и локальные режимы обслуживания с альтернативами. Текущий fixed-K prototype сам K и состав не решает. Продление можно показывать как отклонение от оценённого обычного режима, с неопределённостью и без выдуманной причины. Во всех интерфейсах должен действовать один state/query contract.

Аппаратные стрелки, protected/permissive semantics и состояния ненаблюдаемых секций остаются alternatives/UNKNOWN без независимой схемы или сигналов. Совместное движение само по себе не доказывает совместное разрешение.

Для независимо проверенной высокой точности потребуется отдельная программа validation: новые перекрёстки и сеансы, 3/4 подхода, shared movements, разные нагрузки и режимы, независимые signal references, переносимость calibration. K, состав, границы, интервалы и физические секции оцениваются раздельно; нижние доверительные границы качества — на независимых сеансах, а не на множестве коррелированных автомобилей.

**Практический выбор сейчас:** сохранить корректное likelihood/renewal ядро как reference, исправить два краевых контракта, перейти к bounded inference и провести один реальный пилот. Synthetic 29/34 — подтверждённый результат условной модели; улучшением real raw19/34 или точностью ламп он не является.
