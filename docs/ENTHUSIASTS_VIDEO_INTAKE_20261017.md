## Почему JSON ещё не сопоставлен

В data найден архив с именем «Ленина-Энтузиастов05.10.24.zip». **Внутри6 JSON
имеют имена6_2025_2_23_13..18.json**. Прочитан только первый целый record каждого
entry, суммарно720896 uncompressed prefix bytes (не полные JSON). Их top-level
millis и detection millis, если трактовать как Unix ms в UTC+5, дают23.02.2025;
первый detection первого entry —13:52:47.177. Filename date не подтверждает
соответствие видео, а эти timestamps не совпадают с изображённой датой.

Из Инфо.docx сохранены только относящиеся к millis абзацы с SHA документа:
top-level — время, когда ТС уехало; detection — время обнаружения; отдельно
прямо указано, что при offline processing millis может не совпадать с реальным
временем события. Это допускает другую шкалу, но **не устанавливает** конкретный
offset/drift или тождество сеансов. Ранее сообщённое пользователем происхождение
H1 timestamps «из часов камеры» не сертификат этого нового источника.

Текущий статус paired JSON/video evaluation: **UNAVAILABLE_UNVERIFIED_CLOCK_LINK**.
Не сопоставляли сигнальные циклы и не подгоняли offset по GREEN. Следующий нужный
шаг — подтверждённая frame/PTS↔detection association от producer либо несколько
однозначных same-car correspondences в разных частях записи, с проверкой drift/
нелинейности. Для геометрии не переносился H1 transform другого перекрёстка.
До этого нельзя измерять ошибку реконструкции JSON относительно этих4 transitions.
Блокирована только совместная оценка; само видео пригодно для независимой разметки.
